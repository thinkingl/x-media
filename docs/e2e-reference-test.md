# X-Media 基准参照式端到端测试方案（Reference-based E2E）

> 配套文档：`test-plan.md`（Mock 三角验证，L1–L4 分层）、`design.md`（媒体管道标准）。
> 本文定义一种**以内容为锚点的全真端到端测试**：手工生成带帧号/可校验音频的基准 MP4，
> 经真实 Source→Pipe→Sink 链路推送，ffmpeg 拉流解码后与基准逐帧对齐比对，
> 定量验证丢帧、乱序、重复、内容不一致、音视频不同步与节流漂移。

## 1. 动机与目标

现有 L4 测试只验证"能解码、无致命错误"，**不验证内容是否正确**，也无法在长时间
拉流下发现"偶发丢帧/卡顿"。近期实际暴露的两类 bug 正需要内容锚定的长期验证：

| Bug | 表现 | 现有测试为何测不出 |
|---|---|---|
| readLoop 泄漏 | 重复实例争抢，帧计数跳变 | 只看"无错误"，不比对帧序 |
| 节流漂移（3% 累计） | 拉流越久越滞后，~17s 后 VLC 缓存欠载卡顿丢帧 | 短拉流测不出累计效应 |

目标：提供一套**确定性、可定量、可定位丢帧层**的端到端基准测试，作为回归防线。

## 2. 总体架构

```
┌────────────── 生成器（Go，确定性） ──────────────┐
│  ① 逐帧渲染参考图（帧号条码 + 七段数字 + 主色）    │
│  ② 逐块生成参考音频（DTMF 双音编码块号）          │
│  ③ 写 metadata.json（参数 + 期望序列）            │
│  ④ ffmpeg 编码 → reference.mp4                    │
└──────────────┬───────────────────────────────────┘
               ▼
┌────────────── 被测链路（真实组件，进程内） ───────┐
│  MP4Source → DefaultPipe → RTSP / HTTP-FLV sink  │
└──────────────┬───────────────────────────────────┘
               ▼
┌────────────── 校验器（Go，解析 ffmpeg 输出） ─────┐
│  ffmpeg 拉流解码：视频帧号解码 + 音频块特征解码     │
│  → 与 metadata 期望序列逐帧对齐比对                │
│  → 报告：丢帧/重复/乱序/损坏/AV偏差/节流漂移       │
└──────────────────────────────────────────────────┘
```

关键点：**基准是编码前的原始数据（帧号序列、音频块号序列），不是 MP4 文件本身**。
MP4 是待测输入；校验对象是解码后从内容中读出的帧号/块号，天然抗有损、抗 RTP 重基时间戳。

## 3. 参考数据设计（基准）

### 3.1 视频参考帧

设计原则：**校验必须容错有损编码**（H.264/H.265 有损，禁像素级对比）；帧号须能
从解码帧中**程序化稳定读出**（禁用 OCR）。全部用纯矩形绘制，零字体依赖、完全确定。

单帧布局（分辨率建议 640×360 起步，编码后仍清晰）：

| 区域 | 内容 | 用途 |
|---|---|---|
| 左上 | **帧号条形码**：同步头 + 24bit 帧号 + 8bit CRC8，每 bit 一格 ≥16px | 自动校验主信号 |
| 右上 | **7 段数码显示帧号**（6 位，纯矩形画段） | 人工/截图抽查 |
| 全帧 | 纯色背景：`灰度 = frame_no % 256` | 低成本全局校验（主色统计） |
| 底部 | 固定网格角标 | 检测相邻帧串扰/内容错乱 |

- 条码抗有损：格子 ≥16px，解码时逐格平均亮度 + Otsu 阈值；H.264 crf≤28 下黑白分离稳定。
- CRC8 失败 ⇒ 标记"该帧无法校验"（计数，不判不一致）；**前一个 GOP 的帧允许失败**（RTSP
  中段加入的已知现象，见 §6）。
- 背景主色校验：解码帧主色应 = `frame_no % 256`，主色不符 ⇒ 内容不一致。

### 3.2 参考音频

设计原则：不要求可播放，只要求**每块可识别索引且内容可校验**，并容错 AAC 有损与编码器延迟。

- 参数：**48kHz / mono / s16le**（与 AAC 默认帧长 1024 样本对齐，一块 ≈21.3ms）。
- 每块（1024 样本）编码 1 个 **4bit 半字节**：DTMF 行频 × 列频 双音
  （行：697/770/852/941 Hz，列：1209/1336/1477/1633 Hz，4×4=16 组合）。
- 每 **2 块拼接一个 8bit 块号**（0–255，覆盖 256 块≈5.5s/圈）；长流用 3 块 12bit。
- 校验：对每块做 FFT，找两个主峰频率 → 查表得半字节 → 拼块号。
  AAC 对稳态双音保存良好，峰值清晰；容差 ±10Hz。
- 无主峰（静音/噪声）⇒ 标记不可用（容忍，不判不一致）。
- AAC priming：编码器头/尾有延迟与 padding，校验器允许开头滑动窗口找首块、忽略尾部静音块。

### 3.3 元数据 `metadata.json`

```
{ "video": {"codec":"h264","w":640,"h":360,"fps":30,"total_frames":600,"gop":60,"bf":3},
  "audio": {"codec":"aac","sample_rate":48000,"channels":1,"frame_size":1024,"total_blocks":1024,
            "nibbles_per_block":2},
  "loop": false,
  "scenario": "short-bframes" }
```

期望序列（视频帧号 1..N、音频块号 0..M-1）由参数隐式导出，不必显式存全表。

## 4. 生成与编码流程

```
gen --frames 600 --fps 30 --res 640x360 --bf 3 --audio on --out <dir>
  ├─ frames/frame_000001.ppm .. frame_000600.ppm   （纯矩形绘制，确定性）
  ├─ audio.raw                                       （s16le PCM，确定性）
  ├─ metadata.json
  └─ reference.mp4   （ffmpeg 编码 + 封装）
```

- ffmpeg 视频：`-framerate 30 -i frame_%06d.ppm -c:v libx264 -preset veryfast -crf 23
  -pix_fmt yuv420p -g 60 [-bf 0|3] -threads 1`；H265 用 `libx265`。
- ffmpeg 音频：`-f s16le -ar 48000 -ac 1 -i audio.raw -c:a aac -b:a 128k`。
- 封装：两路 `-c copy -shortest` 合成 `reference.mp4`。
- 确定性：生成器无随机；编码固定参数并 `-threads 1`（ffmpeg 编码字节级确定性，不强依赖，内容可校验即可）。
- **产物策略**：每次测试运行时生成到临时目录（生成 <5s）；可选缓存到
  `server/test/e2e/artifacts/`（gitignore）按 metadata 哈希复用。

## 5. 校验器设计

### 5.1 视频校验
- 输入：ffmpeg 输出的灰度帧流；输出：帧号序列 `[f1, f2, …]` + 每帧状态（OK/CORRUPT）。
- 条码解码：同步头定位 → 逐格亮度 → Otsu 阈值 → 读 32bit → CRC8 校验。
- 对齐：允许**开头前一个 GOP** 的帧缺失/损坏（连接加入点）；从首个校验成功帧起，
  期望后续帧号**严格递增连续**（ffmpeg 输出 display order，B 帧重排不影响帧号单调）。
- 判定：
  - 期望 `n` 实际 `n+k(k>1)` ⇒ 中间 **k-1 帧丢失**（丢帧计数，记录位置）；
  - 帧号回退/重复 ⇒ 乱序/重复帧（异常）；
  - CRC 失败或主色不符 ⇒ 损坏帧（计数）。
  - 循环流（loop）：期望序列 `1..N, 1..N, …`，检测到 `N→1` 视为正常回绕。

### 5.2 音频校验
- 输入：ffmpeg 输出 s16le PCM；输出：块号序列 + 每块状态。
- 分块 1024 样本 → FFT 双主频 → DTMF 查表 → 半字节 → 拼接块号。
- 对齐与判定：同视频（允许 AAC priming 偏移与尾部 padding；块号不连续 ⇒ 丢块）。

### 5.3 音视频同步（跨轨）
- 独立对齐后换算到统一时间轴：视频帧 `n → t=n/fps`，音频块 `b → t=b*1024/48000`。
- 计算平均 Δ = t_audio − t_video（以视频为基准），断言 |Δ| < 容差（建议 40ms≈1.2 帧）。
- 独立拉流两次也能做（内容自带时间信息，不依赖同一连接）。

### 5.4 节流漂移回归（本次 bug 的针对性回归）
- 拉流固定 `T` 秒（如 60s/180s），实际收到帧数 `F`：期望 `F ≥ fps*T − 容差`（容差含加入 GOP）。
  修复前 180s 仅 ~1746 帧（29.1fps）vs 期望 ~5400；修复后 ~5396。**count 断言即可抓住回归**。
- 增强：校验器记录每帧到达墙钟，滑动窗口算有效帧率，断言无单调漂移（可选，先做 count 断言）。

## 6. 执行架构（两层）

### 6.1 进程内 E2E（主，`make e2e`）
- 复用真实组件：`NewMP4Source → NewDefaultPipe → NewRTSPSink/NewHTTPFLVSink`，绑定 `127.0.0.1:0`。
- ffmpeg 子进程拉流解码：
  - 视频 pass：`ffmpeg -rtsp_transport tcp -i <url> -t T -vf "crop=条码区+色块区,format=gray" -f rawvideo -`
    （输出仅 ~30KB/帧，600 帧 ≈18MB，管道解析友好；低分辨率全帧缩略 pass 可另开，检测内容错乱）。
  - 音频 pass：`ffmpeg -rtsp_transport tcp -i <url> -t T -vn -f s16le -`。
- **前置要求**：`RTSPSink`/`HTTPFLVSink` 需暴露绑定地址访问器（当前只有 `media` 包内的
  未导出测试助手 `sinkListenerAddr`），建议给 sink 增加公开 `Addr()/URL()` 方法（见 §9 开放问题）。
- 不依赖 server 二进制，可常规 `go test` 化（但需 ffmpeg，缺失时 `t.Skip`）。

### 6.2 全服务 E2E（可选，`//go:build server_e2e`）
- 起真实 `x-media-server` 二进制 + REST 创建 input/output/pipe/start，ffmpeg 拉流同 §6.1 校验。
- 默认关闭（需真实二进制与 DB），CI 可选 Job。

## 7. 测试矩阵

| # | 场景 | 编码 | 输出 | 关键断言 | 优先级 |
|---|---|---|---|---|---|
| E1 | 短流 H264+B帧 | libx264 `-bf 3` | RTSP(TCP) | 全帧号对齐、零丢失、零损坏 | P0 |
| E2 | 短流 H264 无B帧 | libx264 `-bf 0` | RTSP(TCP) | 全帧号对齐、零丢失 | P1 |
| E3 | 短流 H265 | libx265 | RTSP(TCP) | 全帧号对齐（含 7 段/条码 H265 下可读） | P1 |
| E4 | 循环流 | libx264 | RTSP(TCP) | 多圈对齐、帧号周期回绕正常 | P0 |
| E5 | **长流漂移** | libx264 | RTSP(TCP) | 60–180s 帧数 ≈ fps×T、无累计漂移 | **P0** |
| E6 | HTTP-FLV | libx264 | HTTP-FLV | 全帧号对齐 | P1 |
| E7 | 音视频+同步 | libx264+aac | RTSP(TCP) | 音视频独立对齐 + Δ 在容差内 | P1 |
| E8 | UDP transport | libx264 | RTSP(UDP) | 丢包可容忍但**必须报告丢包率**，帧号仍尽量连续 | P2 |

## 8. 失败诊断（丢帧分层定位）

三层埋点对账，快速定位丢在哪一层：
- **source 层**：现有日志 `MP4 source heartbeat`（每 300 帧）→ source 实际产帧数。
- **sink 层**：现有日志 `RTSP sink WriteFrame` → sink 实际写帧数。
- **decoder 层**：ffmpeg 解码错误 + 校验器读到的帧号数。

任何两层计数不一致 ⇒ 丢帧发生在中间环节；三处一致但校验失败 ⇒ 内容损坏/编码问题。
失败时输出：丢帧位置表（期望帧号 vs 实际）、首坏帧的条码/缩略图 dump 到 artifacts 便于人工查看。

## 9. 实施步骤

1. **生成器** `server/test/e2e/gen/`：PPM 渲染（条码/七段/主色）+ PCM（DTMF）+ metadata.json + ffmpeg 封装。
2. **生成器自检** `gen/gen_test.go`：确定性（两次生成一致）；**编码→解码自循环**（先证明基准本身可被可靠读出）。
3. **校验器** `server/test/e2e/verify/`：视频条码解码、音频 DTMF 解码、对齐比对、报告。
4. **进程内 E2E**：RTSP/HTTP-FLV sink + ffmpeg 子进程，落地 E1/E2/E4/E6。
5. **长流回归** E5（count 断言）——本次漂移 bug 的回归防线。
6. **H265 / 音视频同步** E3/E7。
7. **全服务 E2E**（可选 tag）+ Makefile target：
   ```makefile
   e2e:
       go test -tags e2e ./test/e2e/... -v -count=1
   ```

### 10.3 已知问题 / 后续发现

1. ~~**A/V 变速（音频基轨）**~~ **已修复**：原 readLoop 每迭代每轨只发 1 帧、以基准轨节奏
   推进，AAC padding 使音频轨略长成为基准 ⇒ 视频突发（46.875 帧/s）+ 每圈停顿 ~3.6s，
   回绕边界解码器大量错误隐藏。**修复**：非基准轨按媒体时间对齐补发多帧
   （`emitNext` + `peekMediaAbs`，见 `mp4_source.go`），音视频各按自身帧率平滑输出。
2. **RTSP join 首 GOP 解码伪影**：新 reader 加入时首 GOP 帧解码错误隐藏为重复帧
   （实测 ~48 帧重复，读作首可解码帧号），已通过"首 GOP 豁免"吸收；连接侧仍有
   `Could not find ref` 警告。
3. **回绕边界偶发 1~2 帧丢失/重复**：loop 回绕处解码器瞬时伪影（实测 0~2 帧，随机），
   校验按 `回绕次数×2` 计入容差预算；周期内部仍要求零丢失零重复。
4. **UDP / 多输出 / H265 / 全服务 E2E**：未实现，属后续扩展。
